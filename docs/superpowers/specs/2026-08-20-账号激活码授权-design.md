# 账号 + 激活码授权设计

日期：2026-08-20

## 目标

把现在「全员共用一个密码」换成「一人一账号、一码一账号」，为将来卖激活码做准备。
前期注册即自动发码（自己人用），后期改成码进后台由本人发放（卖码）。

## 前提与边界

- 纯静态站做不到注册、登录、校验激活码，必须加后端。选定 **Cloudflare Workers + D1**
  （免费额度对这个量级绰绰有余，边缘节点在新加坡/雅加达，印尼访问快）。
- 内容最终在浏览器里解密，**拿到内容的人技术上总能导出明文**。账号+激活码挡的是
  随手转发，挡不住蓄意扒取。用户量小、卖给认识的人，这个强度够用。
- `lib/provider.js` 从第一版就留了 `RemoteProvider` 的位置，UI 层不用改。

## 体验：联网只发生在登录与续期

- 词库、对话、语法仍是**静态加密文件**，放在 GitHub Pages，Service Worker 照旧缓存。
  翻词卡、朗读、查语法全是本地操作，与现在无差别。
- 服务器只负责「确认你是激活用户 + 下发内容密钥」。密钥存本地，**30 天内不必联网**。
- 代价：离线超过 30 天需联网续一次。这是「可吊销」的必然代价 ——
  要永久离线就不可能吊销。

## 接口

Workers 上四个接口，全部 JSON over HTTPS：

| 接口 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `POST /register` | email, password | code?（前期返回明文）/ codeIssued（后期） | 建账号，当场生成一张码绑定到该账号（不设过期），并推送 Telegram |
| `POST /login` | email, password | token（30 天） | 密码校验通过发会话令牌 |
| `POST /activate` | token, code | ok | 校验码属于该账号（若带过期时间则校验未过期），绑定生效，账号转已激活 |
| `POST /request-code` | token | ok | 待激活账号作废旧码、生成新码重推 Telegram；已激活直接返回；限流每 IP 每小时 3 次 |
| `GET /content-key` | token | cek, contentVersion, expiresAt | 仅已激活账号可取 |

失败一律返回统一结构 `{ error: "..." }`，中文文案由前端映射，服务端只给稳定错误码。

## 数据表（D1）

实际落地是五张表，比最初设计多了限流用的 `attempts` 和排障用的 `error_log`：

```sql
accounts(id, email UNIQUE, password_hash, salt, status, created_at)
codes(code_hash UNIQUE, account_id NULL, issued_at, used_at, expires_at NULL)
content_keys(version, cek, is_current, created_at)
attempts(ip, endpoint, ts)
error_log(id, ts, method, path, name, message)
```

- `status`：`pending`（未激活）/ `active` / `disabled`（吊销）。
- 激活码只存哈希，与密码同理 —— 数据库泄露也拿不到可用的码。`account_id` 为空表示
  这张码尚未被任何账号绑定；`AUTO_ISSUE_CODE=false` 时靠 `tools/issue-code.mjs`
  预先批量生成、只把哈希灌进这张表，明文由本人手动发放。
- `expires_at`：码的失效时间戳。**已取消过期机制**（2026-08-22 起）：`/register`、
  `/request-code` 生成的码与 `tools/issue-code.mjs` 预生成的散码一样，都不设过期
  （NULL）。理由见下面「为什么取消过期」。库里仍留着改动前发出的一批带真实
  `expires_at` 的旧码，`/activate` 对它们的过期校验没有删——只是新码不会再带这个值。
  `expireCodesOfAccount`（`/request-code` 作废旧码时调用）把 `expires_at` 置成 0
  表示「已作废」，与 NULL（未过期/长期有效）区分开，复用同一条 `expires_at < now`
  判断，不需要额外的 `revoked_at` 列。
- `content_keys` 保存历次内容密钥，换版本时新增一行并把旧行 `is_current` 置 0。
- `attempts` 记录每次限流检查的 `(ip, endpoint, 时间戳)`，配 `idx_attempts` 索引；
  `/login`、`/activate` 每分钟 10 次，`/register`、`/request-code` 更严格（每小时 3 次，见下）。
- `error_log` 记录 Workers 里未被业务逻辑捕获的异常（方法、路径、错误名、错误信息），
  纯排障用，不影响主流程（记不下去也不报错）。

## 安全处理

- **密码**：PBKDF2-HMAC-SHA256，10 万次迭代（Cloudflare Workers 硬上限，原定 60 万在真机被拒），每账号独立 16 字节盐，只存哈希。
  服务端与本人都拿不到用户明文密码。
- **会话令牌**：HMAC 签名的紧凑令牌（账号 id + 过期时间 + 签名），密钥存 Workers Secret。
  无状态校验，不必查库。
- **限流**：同一 IP 对 `/login`、`/activate` 每分钟 10 次上限，防暴力试码；`/register`
  没有会话保护、Worker 地址又公开在前端源码里，限得更严——每小时 3 次，防自助批量开号
  刷爆 D1 免费写配额；`/request-code` 同样每小时 3 次，防止反复点「重新申请」刷爆负责人
  的 Telegram。
- **激活码格式**：16 位大写字母数字，去掉易混字符（0/O、1/I/L），四位一组显示。
- **传输**：Workers 默认 HTTPS；CORS 只允许 Pages 域名。

## 两种发码模式（已改为卖码模式为主）

环境变量 `AUTO_ISSUE_CODE` 控制，改配置重新部署即可，不改代码。**两种模式下
`/register` 都会当场生成一张码、直接绑定到刚建的账号**（一码一账号，不设过期，
长期有效），且都会推送到负责人 Telegram；区别只在于响应里是否带明文码：

- `true`（前期，自己人用）：响应带明文码，注册成功页当场显示 + 复制按钮。
- `false`（后期，卖码模式）：响应不带明文码，页面提示「激活码将由管理员发放，
  请联系管理员获取」；明文码只在 Telegram 推送里能看到。

负责人可能不在线（睡觉等），待激活用户可以调 `POST /request-code` 作废旧码、
申请新码重新推送，不必等负责人上线才有路可走。

## 为什么取消过期

这套系统是「一码一账号」：码从注册那一刻起就绑定到那个账号，且 `/activate`
要求先登录（有效令牌）才能提交码——单有码明文没用，还得有那个账号的邮箱和
密码。能被过期时间挡住的滥用场景，早已被「码绑账号」+「必须先登录」这两道
锁挡住，过期时间挡不住任何额外的实际威胁；而代价是真实的——半夜注册、负责人
在睡觉，几小时后码作废，用户还得自己摸索重新登录、点「重新申请激活码」。
负责人裁定取消过期，僵尸码（已绑账号但从未激活）改由负责人用 `tools/admin.mjs
codes --stale` 查看、`prune-codes --yes` 定期清理。

本期仍不做邮箱验证——它只防假邮箱，而买家是熟人介绍，假邮箱不构成实质问题；
Telegram 推送替代了原计划的发信服务（Brevo/Resend），链路更短、无需自有域名。

## 前端改动

- 新增 `lib/remote-provider.js`：与现有 `provider.js` 同签名（`init` / `unlock` / `lock` /
  `getPacks` / `getDialogs` / `getGrammar`），内部改为「令牌 + 服务器下发 CEK」；另有
  `register` / `login` / `activate` / `requestCode` 供新视图调用。
- 新增视图：注册、登录、激活码展示（自己人模式）、激活码待发放提示（卖码模式，
  `renderCodePending`）、激活（带「重新申请激活码」入口）。现有 `unlock.js`（输密码）
  在过渡期保留。
- 本地存储：令牌与 CEK 存 localStorage，带 `expiresAt`；过期即回登录页
  （复用现有「内容已更新，请重新输入密码」那条回落路径）。

## 吊销

后台把账号置 `disabled`，该用户本地密钥最多 30 天后过期，续期时被拒。
已下载的加密包仍在其手中，但换内容版本后拿不到新密钥。

## 过渡

新旧并存：共享密码模式继续可用，新账号走新流程。确认新流程跑顺后，
下一个内容版本停止发布旧模式所需的 `keys.json`，旧模式自然失效。

## 测试

- Workers 侧：注册重复邮箱、密码错、码已被占用、码过期（`code_expired`）、
  未激活取密钥、令牌过期、限流触发（含 `/request-code` 每小时 3 次）。
- `server/src/notify.js`：假 `fetch` 验证 Telegram 请求的 URL/body 结构；
  缺少 token/chat id 时跳过；`fetch` 抛错或返回非 2xx 时不影响主流程，只记 `error_log`。
- 前端侧：`remote-provider` 用假 fetch 跑通五个接口的成功与失败路径（含
  `requestCode`）；离线（fetch 抛错）时用本地缓存的 CEK 继续可用，过期后回登录页。

## 不做

- 学习进度同步（项目一贯不记进度）。
- 找回密码（本期账号少，手动重置）。
- 支付、订单、自动发货。
